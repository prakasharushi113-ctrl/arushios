AERO FLAPPY

Aero Flappy is a custom 2D Flappy Bird-style game built to run on an ESP32 with a 320×240 ILI9341 display. It combines a playable arcade game with a custom Frutiger Aero-style desktop interface — the game runs inside an Aero PC window, where you guide a small cat character through moving poles while avoiding collisions. The aim was a complete game experience on an embedded microcontroller rather than a regular PC or Raspberry Pi.

Hardware: ESP32 Dev Module as the main controller (running the game and handling GPIO input plus display control), an ILI9341 320×240 TFT for the Aero desktop, game window, character, poles, score, and Game Over screen, and three physical buttons — GPIO 27 for Flap, GPIO 26 for Start/Restart, GPIO 25 for Pause/Resume. Display wiring is CS on GPIO 5, DC on GPIO 15, RST on GPIO 4, all over SPI.

Software: written in C/C++ using the Arduino IDE, on the ESP32 Arduino platform. Display and drawing runs through the Adafruit ILI9341 and Adafruit GFX libraries, with custom bitmap header files — Aero_pc.h, catty.h, pole.h, and two Game Over headers — holding all the artwork.

How it works: the ESP32 drives the game state and talks to the display over SPI. On boot, the Aero PC desktop shows first; pressing Start begins the game, with the cat sitting still until the first flap. Gravity constantly pulls the cat's vertical velocity down, while Flap gives it an upward kick. Poles scroll right to left, and clearing one increases the score. The game checks the cat against both the poles and the window boundaries — a hit triggers the Game Over overlay, and Pause simply freezes gameplay updates until pressed again.

  • Custom Frutiger Aero desktop and Aero PC game window
  • Flappy Bird-style gameplay with custom cat and pole graphics
  • Flap, Start/Restart, and Pause/Resume controls
  • Score tracking with pipe speed that increases gradually
  • Gravity, flap physics, and collision detection
  • Buffered (RAM-composed) rendering to cut down on display flicker
  • Custom Game Over window layered over the Aero PC interface

Technical details: 320×240 resolution on an ILI9341 controller over SPI, using RGB565 bitmap graphics. Frames are composed in RAM buffers before being sent to the display to reduce visible flicker. Pipe speed starts low and ramps up with score, capped at a maximum, and collision detection compares the cat's hit area against both poles and window boundaries.

My custom work: I designed the Aero PC interface, the Catty character artwork, the pole artwork, and the Game Over screens myself, then prepared all the bitmap graphics as header files for the ESP32. The game software itself — physics, scoring, pipe movement, collision detection, button controls, pause behavior, Game Over behavior, and the buffered rendering fix for flicker — was also built specifically for this project.

Status: assembled and tested on real hardware — the Aero desktop, game window, and Catty/pole graphics are all working on the ESP32 display. Controls (Start/Restart, Flap, Pause/Resume) are in place, and gameplay has been tuned by adjusting jump strength, pipe speed, spacing, gap size, and difficulty ramp. The Game Over screen has been tested on hardware and is being refined to render cleanly as a smaller overlay window without leaving artifacts — currently a working prototype in the refinement stage.

BUBBLEGUM BITCH RUN

Bubblegum Bitch Run is a custom 2D running game for an ESP32 and a 2.8" ILI9341 TFT display. You run through a scrolling world, dodge an Anti-Hero chasing from behind, collect coins, and manage a limited number of lives — built as a full interactive system rather than just a display demo.

Hardware: ESP32-D0WD-V3 dev board as the main controller, a 2.8" ILI9341 TFT over SPI for backgrounds, characters, menus, coins, lives, and attack graphics, two push buttons — GPIO 27 for fast run/dodge and GPIO 26 for normal run — and a buzzer, tested separately on an Arduino Uno as a first step toward sound effects.

Software: C++ via the Arduino IDE, using the Adafruit GFX and Adafruit ILI9341 libraries for graphics and display control, over SPI. Every sprite — backgrounds, player frames, Anti-Hero, coins, lives, attack graphics, effects, and the intro image — is stored as custom bitmap/header C/C++ data.

How it works: the ESP32 continuously reads the two buttons and updates the player's movement and animation state. The player's position is tracked in world coordinates while a separate camera position decides what part of the world is visible on the TFT. Backgrounds are stored as bitmap data, and each frame the program picks the right background section for the current world position and combines it with coins, the Anti-Hero, the player, life indicators, attack effects, and the score. The Anti-Hero constantly moves toward a point just behind the player, and once it's close enough it can trigger an attack — fast-running doubles as the dodge mechanic during that window.

  • Custom intro/title and start-game screens
  • Running player animation with normal/fast movement
  • Anti-Hero chase AI with flying/idle behavior and a dedicated attack pose
  • Diagonal attack effect aimed at the player
  • Three-life heart system and a coin collection/scoring system
  • Multiple backgrounds stitched into one scrolling world
  • Game-over and restart flow
  • Chunk-based rendering to cut down on TFT flicker

Technical details: 320×240 resolution on an ILI9341 controller over SPI, using RGB565 bitmaps with separate transparency masks for sprites. Rendering builds the screen in 40-pixel-high chunks inside a 320×40 RGB565 buffer before sending each chunk to the display. Animation uses timed, state-based frame switching, collision detection is simple rectangular overlap (for both coins and attacks), and inputs are digital GPIO with internal pull-up resistors.

My custom work: I designed and programmed the full game logic and structure, built the player movement/animation system, the Anti-Hero following behavior, and the attack/dodge/life mechanics from scratch, plus coin placement/collection/scoring, the world/camera system, and the chunk-based renderer specifically built to solve TFT flicker. I also created and integrated every bitmap asset — characters, backgrounds, UI elements, attacks, effects, coins, lives — and designed the intro, start-game, and game-over screens.

Status: playable prototype — the TFT display, character movement and running animation, multiple backgrounds, Anti-Hero following, coin collection, score display, intro/start screens, and the basic three-life and attack systems are all implemented and tested. Current focus is refining the Anti-Hero's attack/dodge timing — making the attack effect travel correctly toward the player and making fast running a genuine reaction-based dodge rather than permanent protection. The buzzer and additional sound effects are being explored separately.

DESK COMPANION

Tara is a custom-built physical AI companion combining AI, Python, embedded electronics, display graphics, voice interaction, and gaming — the goal is an AI character that exists as a real physical device rather than just a chatbot on a screen.

Hardware: ESP32 as the main microcontroller for the physical interface and game, a 2.8" ILI9341 TFT display for Tara's face and game graphics, two push buttons (one for reset/game-select/start, one for pause/resume), a potentiometer planned as the controller for the in-built Space Shooter, a speaker for Tara's spoken responses, and custom rocket/alien artwork made specifically for the game.

Software: Python runs Tara's main backend — AI interaction, memory, web search, weather lookups, speech, and serial communication with the ESP32. The ESP32 side is written in C++ via the Arduino IDE, handling the TFT and game hardware. A database stores Tara's long-term memory, and a custom Python bitmap converter was built from scratch to turn PNG sprites into Arduino-compatible RGB565 bitmap data with transparency masks.

AI features: Tara can hold normal conversations while keeping context, and has a memory system that stores and recalls important information later. The backend handles everyday conversation, web searches, weather info, memory-related requests, and voice responses.

Expressions & display: the TFT acts as Tara's face and interface, with expressions including idle, happy, angry, crying, and thinking/looking — her expression shifts depending on the conversation, while responses are shown on-screen. The Python backend talks to the ESP32 over serial commands.

Space Shooter game: a game being built directly into Tara, featuring a custom rocket, alien enemies, bullets, rocket movement via the potentiometer, collision detection, scoring, and pause/resume. Button 1 resets Tara's text, selects the game, and starts it; Button 2 pauses/resumes; the potentiometer steers the rocket.

Custom graphics pipeline: instead of an existing image-conversion library, I built a custom Python converter for the game graphics — it processes the raw PNG artwork, handles the background, converts pixels to RGB565, generates a transparency mask, and outputs a `.h` file ready to include directly in the ESP32/Arduino project.

Status: the core Tara system — TFT communication, expressions, memory, and the Python backend — is up and running, and a basic shooter concept has already been tested on an Arduino Uno. Current focus is porting the full game onto the ESP32 and integrating the rocket, aliens, bullets, controls, collision detection, and scoring into Tara's existing system.

SMART AGRICULTURE

An IoT and machine-learning based smart agriculture system for real-time monitoring of environmental and soil conditions, built to catch crop problems early instead of relying on slow, symptom-only manual inspection. Built as a team project — my individual work covered the Node.js backend, the React website, the data visualizations, and the complete ML pipeline.

Hardware: Raspberry Pi 4 as the main controller and processing unit, a DHT22 sensor for air temperature/humidity wired directly over GPIO, an integrated soil sensor reading moisture, temperature, pH, electrical conductivity, and nitrogen/phosphorus/ potassium, and a USB-to-RS-485 adapter bridging the soil sensor to the Pi.

Software: React for the web dashboard, a Node.js backend I built myself, Firebase as the live cloud database for streaming sensor readings, and four ML classifiers compared against each other — Random Forest, Decision Tree, KNN, and SVM.

How it works: the DHT22 and soil sensor periodically collect readings — the DHT22 over GPIO, the soil sensor over RS-485. The Raspberry Pi reads both and pushes the data to Firebase, which stores and streams it live. The React site pulls from Firebase to show real-time readings and graphs. For prediction, historical sensor data was used to train supervised classifiers, and the trained model now takes live Firebase values and predicts the current crop state on the fly.

  • Continuous air and soil condition monitoring
  • Live sensor dashboard with historical trend graphs and out-of-range alerts
  • Real-time crop-state prediction from live sensor data
  • Classifies into Healthy, Nutrient Deficiency, Powdery Mildew, or Salt Stress

Technical details: the ML model takes 9 input parameters — air temperature, air humidity, soil moisture, soil temperature, soil pH, EC, nitrogen, phosphorus, and potassium. Missing values were handled with mean imputation, and the dataset was split 80/20 train/test with a fixed random state of 42.

  • Random Forest — 99.33% accuracy, 0.99 precision/recall/F1
  • Decision Tree — 99.33% accuracy, 0.99 precision/recall/F1
  • KNN — 96.67% accuracy, 0.97 precision/recall/F1
  • SVM — 62.67% accuracy, 0.82 precision, 0.63 recall, 0.69 F1

Random Forest was selected as the final predictor, correctly classifying 298 of 300 test samples (99.33% accuracy).

My custom work: I designed and built the Node.js backend from scratch, built the entire React dashboard, created all the sensor graphs and visualizations (including low/optimal/high range indicators), and handled the complete ML pipeline — data prep, preprocessing, training and comparing all four classifiers, evaluation, final model selection, and wiring it up to live sensor data.

Status: fully working end-to-end — sensor collection, Firebase streaming, the dashboard, and real-time ML prediction have all been demonstrated successfully. Planned future work includes adding a camera module, multiple sensor nodes, sensor drift calibration, mobile/SMS alerts, and expanding the dataset to more crops and diseases.

A research paper based on this project — IoT and ML-Based Smart Agriculture with Real-Time Plant Disease Monitoring — has been submitted to the IEEE Silchar Conference 2026.
